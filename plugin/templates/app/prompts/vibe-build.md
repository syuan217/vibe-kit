# vibe-build — 按 blueprint 实现

> 用法:`/vibe-clarify` 产出 blueprint 后,对任意 AI 工具说"按 prompts/vibe-build.md 实现需求"。
> (本文件由 `scripts/sync-prompts.py` 从 `plugin/skills/vibe-build/SKILL.md` 生成,勿手改)

需求工作流的**阶段 2**:把 `specs/NNN-需求名/blueprint.md` 的任务清单落地成代码 + 测试。

## 前置

1. 确认 `specs/NNN-需求名/blueprint.md` 存在且有任务清单;没有则提示先跑 `/vibe-clarify`。
2. **改代码前先查 `docs/wiki/code-map.md`** 定位要动的模块(这是硬规则,贯穿所有 skill);查不到再全库搜索,事后补进 code-map。
3. (可选)确认 `tdd` skill(mattpocock/skills,外部依赖)是否可用——可用则对有单测能力的任务用 TDD 方式;不可用或任务不适合(纯配置/契约对齐/遗留代码)则不强求。

## 步骤

1. **垂直切片,逐任务实现**:从 blueprint 任务清单取**一个**可独立验证的任务(一个 seam、一个最小实现),实现它,跑通,再取下一个。**不要"先把所有测试写完再实现"**(水平切片会测到想象中的行为)。每个任务按 blueprint 里写的验收检查点收口。
2. **有单测能力的变更遵循 TDD 原则**(当 tdd 可用时):
   - **红→绿**:先写失败的测试,再写刚好让它过的代码,不写投机性功能。
   - **只在确认的 seam 测试**:测试验证公开接口的行为,不测私有方法、不 mock 内部协作者——否则重构时测试会碎。
   - **独立的预期真值**:断言值要有独立来源,不要"用代码算出来的值去断言代码"(同义反复,永远不会失败)。
   任务不适合 TDD 时(如纯文档/配置/对接外部契约),正常实现并补必要的覆盖即可,不硬套。
3. **行为变更必须有测试**(宪法第 7 条):不合并无测试的行为变更。
4. **实现偏离 blueprint 时**:不要默默改回去、也不要默默偏离。在 `spec.md` 末尾的「实现偏差」节记一句话(为什么偏离、改成了什么)——vibe-verify 会核对一致性,留痕让它能对得上。
5. **每完成一个切片**:跑相关测试,确认绿,再取下一片。全部任务完成后提醒用户:进入 `/vibe-verify`(阶段 3)做两轴核对。

## 不做什么

- 不在本阶段沉淀长期文档(那是 finalize-feature 的事,在 PR 评审通过、合并前)。
- 不跳过测试写实现(红→绿,TDD 可用时)。
- 不一次性把 blueprint 所有任务实现完再测(垂直切片,逐片验证)。
