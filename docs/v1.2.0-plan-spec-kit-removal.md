# 移除 spec-kit、自建 3 阶段需求工作流 — 实施计划(v1.2.0)

> 本文档是 **v1.2.0** 这次大改的设计与核对基准。用于后期核对"改动是否与计划一致"。
> 状态:**内容已实施,待发版**(发版步骤见 §八)。生成日期 2026-07-30,2026-07-31 review 补充模板;
> 同日二轮核对结果与增补见 **§九**(原第四节的 `[x]` 保留当时的实施记录,不回改)。

## 一、背景与动机

原 vibe-kit 以 **spec-kit** 作为需求开发执行引擎(specify/clarify/plan/tasks/implement)。试用后发现两个核心痛点:

1. **产出可读性差**:spec-kit 的 plan/tasks 高度结构化、接近代码,优化的是"AI 可执行性"而非"人可读性",团队评审困难。
2. **提问可读性差**:`/speckit.clarify` 一次性甩一堆结构化问题,人读不懂问题意图。

决定:**移除 spec-kit,自建 3 阶段工作流**,澄清/评审引擎改用 mattpocock/skills(经 vercel-labs/skills 生态安装,保持上游同步,不拷贝进 vibe-kit)。

## 二、核心设计

### 2.1 依赖分层(关键)

| 层 | skill | 分发方式 | 语言 | 谁维护 |
|---|---|---|---|---|
| **流程层**(vibe-kit 自有) | vibe-clarify / vibe-build / vibe-verify / cross-app-spec / finalize-feature / vibe-init 等 | vibe-kit 三套插件清单 + 文档补充 `npx skills add` 兜底 | 中文 | vibe-kit |
| **引擎层**(外部依赖) | grill-with-docs / grilling / grill-me / code-review / tdd | 应用仓库 `npx skills add mattpocock/skills` 安装,上游自动同步 | 英文原装 | mattpocock |

流程层 skill 正文**调用**引擎层 skill 名,不打包它们。

### 2.2 三阶段流程 + 引擎映射

```
单应用: /vibe-clarify 直接启动
跨应用: cross-app-spec(hub 建总 spec) → 各服务 /vibe-clarify

specs/NNN-需求名/  ← vibe-clarify 自建目录(套用 specs/_template/ 骨架)
        │
   ┌────▼──────────────────────────────────────────┐
   │ 阶段1:vibe-clarify                              │ ← specify + clarify + plan
   │   • 自建骨架(spec.md + 三文档模板)              │
   │   • 起草 requirement.md(给人读)                  │
   │   • 调 grill-with-docs 逐个澄清(边问边写)        │ ← 引擎:grill-with-docs
   │   • 产出 blueprint.md(给 AI 执行)               │
   │   • 沉淀 open-questions.md(已决 + 待定留痕)      │
   └────┬─────────────────────────────────────────────┘
        │
   ┌────▼──────────────────────────────────────────┐
   │ 阶段2:vibe-build                                 │ ← tasks + implement + 单测
   │   • 从 blueprint 垂直切片逐任务实现              │
   │   • 有单测能力的变更遵循 tdd(红→绿)              │ ← 引擎:tdd(可选)
   │   • 每任务带验收检查点                            │
   └────┬─────────────────────────────────────────────┘
        │
   ┌────▼──────────────────────────────────────────┐
   │ 阶段3:vibe-verify                                │ ← 传统流程缺失的校验环
   │   • 调 code-review 两轴并行评审                   │ ← 引擎:code-review
   │       - Spec 轴:实现是否忠实 blueprint            │
   │       - Standards 轴:是否符合编码规范             │
   │   • 偏差记进 spec.md「实现偏差」                  │
   │   • 通过后提醒:评审通过、合并前跑 finalize         │
   └────┬─────────────────────────────────────────────┘
        │  (提 PR → 人工评审 → 评审通过)
   ┌────▼──────────────────────────────────────────┐
   │ finalize-feature(合并前)                        │
   │   • 读 requirement/blueprint/open-questions + git diff
   │   • 蒸馏进 docs/wiki、architecture、api、decisions、AGENTS
   │   • 跨应用:回填 hub 总 spec 影响面表 + registry   │
   └─────────────────────────────────────────────────┘
```

### 2.3 两类文档(兼顾人 + AI)

| 文档 | 读者 | 内容 | 模板 |
|---|---|---|---|
| `spec.md` | 骨架 | 元数据 + 需求概述占位 | vibe-clarify 自建 |
| `requirement.md` | 人 | 意图、背景、用户故事、验收场景、范围边界 | `specs/_template/requirement.md` |
| `blueprint.md` | AI | 技术选型、数据模型、契约、任务清单(垂直切片)、检查点 | `specs/_template/blueprint.md` |
| `open-questions.md` | 留痕 | 已决决策 + 待定项(标来源:上级下放/拷问发现) | `specs/_template/open-questions.md` |

### 2.4 澄清可读性:grill-with-docs 四铁律

一次只问一个问题 / 每个问题给推荐答案 / 能查到的事实去查(决策才问人)/ 遍历决策树。

## 三、工作流衔接性验证(7 个边界,全闭合)

| 边界 | 衔接方式 |
|---|---|
| 1. 单应用入口 → vibe-clarify | app/AGENTS.md 动词 `/speckit.specify` → `/vibe-clarify` |
| 2. spec.md 创建 | vibe-clarify 包揽:自建 `specs/NNN-需求名/` + 套用三文档模板 |
| 3. cross-app-spec → vibe-clarify | 启动指令动词替换 + **下放问题作为 grill-with-docs 强制输入** |
| 4. vibe-clarify → vibe-build | blueprint.md 任务清单作为 vibe-build 输入 |
| 5. vibe-build → vibe-verify | code-review 的 Spec 轴读 blueprint.md |
| 6. vibe-verify → finalize-feature | verify 通过后**提醒**(不立即执行)"评审通过、合并前跑 finalize" |
| 7. finalize-feature → 长期文档 | 蒸馏逻辑不变,输入产物名改为 requirement/blueprint/open-questions |

**边界 3 关键衔接**:grill-with-docs 是主动发现问题的拷问引擎,不会自动感知 cross-app-spec 下放的预定义清单。vibe-clarify 必须显式处理:① 检查启动指令是否带下放清单;② 若有,作为 grill-with-docs 强制输入逐个拷问到结论;③ 决策树拷问补充发现新问题;④ 两类问题都进 open-questions.md 标注来源。

**finalize 时序**:触发语 `right after /vibe-verify passes`;正文明确实际最佳时机是 PR 评审通过、合并前。verify 通过只代表"可提 PR",不是"可沉淀文档"。

## 七、关键决策记录

1. **承载形式**:不引入新 CLI,用现有 skill 同源机制 + 模板机制接住 spec-kit 的三件事(CLI/动词/模板)。
2. **mattpocock 落地形态**:不拷贝、不 submodule,作为外部依赖各应用仓库 `npx skills add` 安装(依托 vercel-labs/skills 工具中立生态)。
3. **vibe-init 不自动装 mattpocock**:仅提示(列出常见 agent),避免 npx 网络问题阻断初始化。
4. **constitution 路径**:`docs/constitution.md`(入库、团队可见),非 gitignore 本地目录。
5. **mattpocock 名单**:保留 5 个(grill-with-docs/grilling/grill-me/code-review/tdd),英文原装不本地化。**(二轮 review 更正:对外统一承诺 3 个 —— grill-with-docs / code-review / tdd,grilling 与 grill-me 作为 grill-with-docs 的同源底座只在括注中提及,理由见 §9.2②)**
6. **阶段1命名**:`vibe-clarify`(原拟 vibe-design,用户改为 vibe-clarify)。
7. **spec.md 创建**:vibe-clarify 包揽(用户选),不新增独立 vibe-specify skill。

### 9.2 计划未覆盖的决策(新增改动)

**① `specs/_template/` 进不了应用仓库的 git**(计划遗漏的设计漏洞)。三个新骨架落在 `specs/` 下,而 app gitignore 整体忽略 `specs/`,导致模板永不入库——队友克隆后必须自己跑 vibe-init.sh(且本地要有 kit 路径)才有模板,否则 vibe-clarify 步骤 1 直接断掉。旧设计没这问题:模板在 `.specify/` 下,由公开 CLI `specify init` 重建。

决定:**让模板入库**,它是工具不是过程产物。gitignore 改为:

```
specs/*
!specs/_template/
```

**必须是 `specs/*` 而非 `specs/`**——已实测验证:git 不下降进被整体排除的目录,写成 `specs/` 时负规则静默失效、模板照样不入库。

用户已手动往 `.gitignore` 加过 `specs/` 的仓库自动退回旧行为(模板不入库、各自跑 vibe-init 生成),**不需要检测逻辑**:`vibe-init.sh` 的 gitignore 合并本就是逐行去重追加、不动已有条目,追加进去的两行成为死规则。此情形已写进 vibe-init skill 收尾提示。

同步改动:`plugin/templates/app/gitignore`、`plugin/templates/app/AGENTS.md` 文档地图、`WORKFLOW.md`(§1.1 与目录结构两处)、`scripts/vibe-init.sh` 收尾提示、`plugin/skills/vibe-init/SKILL.md` 收尾。

**② 引擎名单 5 个 vs 3 个不一致**。§2.1 与 §七.5 写「保留 5 个」,根 AGENTS.md 照抄;但其余所有文档(WORKFLOW §1.2 引擎表、app/AGENTS.md、USAGE、README、vibe-init.sh、vibe-init skill)一律只讲 3 个,`grill-me` 全仓库只出现那一次、**无任何用途说明**。

决定:**对外统一承诺 3 个**(grill-with-docs、code-review、tdd),根 AGENTS.md 改为「grill-with-docs(及同源的 grilling/grill-me)」。`npx skills add` 是整包安装,名单写几个不影响安装结果;列出没有用途说明的名字只会让人去找"grill-me 什么时候用"然后找不到。

**③ 名册漂移的工具口子**(问题 ① 的根因之一)。`vibe-release.py` 的 `fix_skill_count_in_docs` 只扫 `README.md` / `plugin/README.md` / `plugin/USAGE.md`,**不含根 `AGENTS.md`**——所以 bump 也兜不住那处「7 个 skills」,下次加 skill 会漏同一个地方。

决定:`AGENTS.md` 加入扫描范围;另给 `check` 加一条 **AGENTS.md skill 名册校验**(按集合比对,不管顺序与括注)。数字报 warning(bump 能自动修)、**名册报 error**——bump 修不了名册,warning 会被无视,而名单错比数字错有害:AI 读 AGENTS.md 会以为某个 skill 不存在。`tests/test_vibe_release.py` 补 4 个用例(名册一致通过 / 名册漂移报错 / 数字漂移只警告 / 无名册行时不校验),40 → **44 passed**。
