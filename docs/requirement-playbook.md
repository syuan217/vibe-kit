# 需求处理手册(Playbook)

> 给所有团队成员:一个需求下来时,照此执行。Claude 用户直接说触发语(skill 自动响应);Cursor/Codex 用户按各仓库 `prompts/*.md` 执行,流程完全相同。

## 第 0 步:判断需求类型

问一个问题:**这个需求需要改动几个服务的代码?**

- 只改 1 个 → 走【单应用流程】
- 2 个及以上 → 走【跨应用流程】
- 不确定 → 在任意已接入仓库对 AI 说"帮我分析这个需求的影响面"(AI 会读 hub registry 判断);仍拿不准就按跨应用走,总 spec 里影响面只剩一个服务时再降级

判断技巧:凡涉及"调用别的服务的新接口 / 改对外接口 / 新增消息"的,几乎都是跨应用——即使你自己只改一个仓库,契约对端也算影响面。

## 单应用流程(开发者一人闭环)

在该服务仓库内依次执行:

| 步骤 | 你做什么 | 产出 |
|---|---|---|
| 1. 澄清+定方案 | `/vibe-clarify <需求描述>`:起草 requirement.md,认真回答 grill-with-docs 的逐个拷问(一次只问一个、每个带推荐答案,**不要跳过**,这是减少返工最有效的一步),产出 blueprint.md | 分支 + `specs/NNN-xxx/`(spec.md、requirement.md、blueprint.md、open-questions.md) |
| 2. 实现 | `/vibe-build`:按 blueprint 任务清单垂直切片逐个实现,有单测能力的变更遵循 TDD(红→绿),每任务带验收检查点 | 代码 + 测试 |
| 3. 核对 | `/vibe-verify`:调 code-review 两轴并行评审(Spec 轴:是否忠实 blueprint;Standards 轴:是否符合规范),偏差记进 spec.md | 核对结论 |
| 4. 提 PR | 按 PR 模板勾检查清单;CI 会检查文档新鲜度 | 评审合入 |
| 5. 收尾 | 评审通过、**合并前**说"需求收尾"(finalize-feature):把 requirement/blueprint 结论沉淀进 docs/、wiki、ADR;若依赖/契约变了,同步 hub registry | 文档与代码一致 |

## 跨应用流程(发起人协调 + 各服务开发者并行)

### 阶段一:立总 spec(发起人,在 hub——位置见任一应用仓库根的 `.vibe-hub` 文件)

对 AI 说:**"这个需求涉及 X 和 Y 服务:<需求描述>"**(cross-app-spec 自动触发),AI 会:

1. **先问你"这个需求最核心、关系最紧密的是哪个服务"** —— 先想好答案,你比语义匹配准;实在说不上来就让它自己猜
2. 以该服务为种子读 registry 图遍历,分析影响面给你确认(存疑的服务会标注)
3. **就跨端问题澄清**(职责归属、兼容策略、失败与幂等语义、一致性要求、上线顺序硬约束)
4. 建 `specs/NNN-需求名/spec.md`:需求概述、影响面表、**待定问题**、**契约变更**、各服务职责拆分与验收标准、上线顺序
5. 为每个涉及服务生成一条**拷贝即用的启动指令**

你需要把关的:影响面是否漏了服务、契约设计是否合理、职责边界是否清晰。

> **第 3 步答不上来是正常的,别硬答。** 它只问"答案不同会改变一个以上服务做法"的问题——这类问题单个服务的 `/vibe-clarify` 结构上问不出来(它只看得到自己那一半)。你不是所有服务的领域负责人,拿不准就让它记进「待定问题」表、注明由谁在什么阶段定。**猜错的答案一旦写进契约,下游会当既定前提照做,比留一个开放问题更难纠正。**
>
> 反过来,只影响一家的细节(按钮放哪、字段叫什么)不该在这里问,会被下放到该服务自己的 `/vibe-clarify`(grill-with-docs 会把下放问题作为强制输入逐个拷问)。
>
> 这个阶段也**不必确定要改哪个接口**——registry 是服务级粒度,只回答"谁被牵涉、怎么交互";具体接口留给各服务实施时读代码发现。

### 阶段二:契约评审(人工闸口,不可跳过)

把总 spec 发给涉及服务的 owner 评审,重点审契约章节(接口定义、兼容性标注)。**先过一遍「待定问题」表——标了"契约评审前定"的必须已有结论**,否则契约是建在未决假设上的。达成一致后把总 spec 状态改为 `contracts-approved`,提交。

**评审通过前,任何服务不得开始实现。** 这一步是跨应用协作质量的关键——契约定稿后各服务才能并行开发互不阻塞。

### 阶段三:各服务并行实现(各开发者,在各自仓库)

每个服务的开发者拿到自己那条启动指令,在自己仓库粘贴执行——之后就是标准【单应用流程】(启动指令已预填总 spec 链接、职责摘要、契约约束、下放问题,vibe-clarify 会把下放问题作为 grill-with-docs 强制输入逐个拷问到结论,子 spec 天然带跨应用上下文)。

各自完成后:回填总 spec 影响面表里自己那行的**分支与状态**。子 spec 在各自仓库的 `specs/` 下,是不入库的过程产物,所以表里记的是"谁、哪条分支、什么状态",不是文件链接。

### 阶段四:上线与关闭(发起人)

按总 spec 的上线顺序发布(通常先提供方、后消费方,注意兼容性约束);全部上线并通过端到端验收后,总 spec 状态改 `done`;依赖关系有变化的,把 registry 中本需求的 `planned` 依赖转为 `active`(合入后 CI 自动重生成依赖图)。

## 角色速查

| 角色 | 职责 |
|---|---|
| 需求发起人 | 判断类型;跨应用时立总 spec、组织契约评审、盯上线顺序与关闭 |
| 服务 owner | 评审涉及自己服务的契约与 registry 变更 |
| 开发者 | 在自己仓库走 vibe-clarify/build/verify 流程 + 收尾;维护本仓库文档 |

## 常见情况

- **做到一半发现要动别的服务**:停下,回 hub 补/升级总 spec(单应用升级为跨应用),补契约评审,再继续。不要"顺手"在对端加接口。
- **紧急线上修复**:可以先修(跳过 spec),但合并后 24h 内补:说"同步文档"(sync-docs)+ 若动了契约,补 registry 与消费方通知。
- **需求做完文档没更新被 CI 警告**:说"需求收尾"或"同步文档",一条命令补齐,不追责。
- **只是重构不改行为**:不需要 spec;改动大时收尾跑一次 rebuild-wiki 防 code-map 失效。
- **合并/rebase 时文档冲突**:先解代码冲突完成合并,然后说"同步文档"(sync-docs)以合并后的代码为准重建文档条目;不要花时间逐行手解文档冲突。长期分支及时回灌 main,减少冲突面(详见 doc-style「分支与文档」)。

## 一图流

```
需求 ──► 改几个服务?
          │
    1 个  │  ≥2 个
    ▼     ▼
 单应用   hub 立总 spec(cross-app-spec:影响面+契约+分工+顺序)
 流程       │
    │     契约评审 ◄── 人工闸口
    │       │ contracts-approved
    │     各服务粘贴启动指令,并行走单应用流程
    │       │
    ▼       ▼
 vibe-clarify → vibe-build → vibe-verify → PR → (评审通过) finalize-feature
                                                              │
                                  按上线顺序发布 → 回填总 spec → done
```
